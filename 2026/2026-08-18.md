### 3\. Special topic: GitHub workflows and the Carpentries Workbench

[*Link: Original announcement on Carpentries mailing list*](https://carpentries.topicbox.com/groups/maintainers/T5c615a4ce182c181-Mcd9283adeaebca93a19bfcaf/improved-workflows-for-workbench-lessons)

**GitHub Actions** is an automated workflow platform built into GitHub that runs tasks on their servers (like testing code, building projects, or deploying applications) triggered by an event or given schedule. A **GitHub Workflow** is the specific YAML configuration file where you define those automated steps and conditions.

All Carpentries lessons have these nine actions and workflows (here using as example the Workbench template):

* https://github.com/carpentries/workbench-template-md/actions

For those nine actions we can group them as:

* The most important one for Maintainers - 01 Maintain: Build and Deploy Site
* Three to update packages in the lesson, update the package cache, and update the worflows (02 to 04 Maintain)
* Five to check, handle, and clean after Pull Requests. See an example here: https://github.com/datacarpentry/spreadsheets-socialsci/pull/202

Workflow files can be complex, but they use a structured YAML grammar which helps us understand what they do:
Every GitHub Workflow YAML file uses a structured grammar. Understanding these core keys helps explain how each file behaves:

|YAML Key|Description \& Function|
|-|-|
|`name`|Human-readable label displayed in the GitHub Actions tab.|
|`description`|Explains what the workflow accomplishes.|
|`on`|**Triggers/Events** that execute the workflow. Examples: `push` (code pushed), `pull\_request` (PR opened/updated), `schedule` (cron schedule), `workflow\_dispatch` (manual button trigger), `workflow\_run` (triggered when another workflow finishes).|
|`jobs`|A workflow consists of one or more **jobs** executed in parallel by default, or sequentially if dependencies (`needs`) are defined.|
|`runs-on`|The operating system for the runner VM (e.g., `ubuntu-latest`, `ubuntu-22.04`).|
|`needs`|Establishes job dependencies (e.g., `needs: preflight` ensures `full-build` only runs if `preflight` succeeds).|
|`steps`|Sequential tasks inside a job:|
|  ↳ `uses`|Invokes a reusable action (e.g., `actions/checkout@v6` or custom `carpentries/actions/\*`).|
|  ↳ `with`|Supplies input parameters to an action.|
|  ↳ `run`|Executes command-line shell commands or R scripts.|
|`outputs`|Passes values between steps or between jobs.|
